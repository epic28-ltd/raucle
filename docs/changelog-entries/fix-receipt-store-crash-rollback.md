# Receipt store crash rollback and recovery

- Segmented receipt store: a segment that carries a .meta seal sidecar while still writable, meaning a seal crashed between the sidecar write and the read-only flip, is never silently resumed or re-sealed. Opening it raises ReceiptStoreSealRefused and the operator resolves the incomplete seal's sidecar; the stale sidecar is never rewritten by the store itself.
- A failed append (write, flush or fsync) now drops the open segment handle, so the next append re-opens the segment and re-validates its tail. A torn record fails closed by name on that resume instead of being silently chained past.
- Seal order hardened: the .meta sidecar is fsynced before the segment flips read-only, so a power cut can no longer leave a read-only segment whose seal sidecar never landed.
- New regression tests pin crash behaviour between an append and its rollover, inside the seal, and after the read-only flip, plus torn-tail refusals on restart and in-process after a failed append, and sealed-segment record tamper and truncation caught on offline verify.
- New regression tests separate telemetry export failure from authoritative receipt persistence failure on the segmented path: an SIEM outage keeps the allow decision, buffers the event by name and leaves the receipt verifiable offline, while a segmented receipt write failure downgrades the decision to deny with the named reason "receipt emission failed" and propagates from _sign_and_store_receipt, extending the coverage PR 361 pinned for the flat writer.
- Honest limitation, reported not fixed: truncation of a sealed segment at an exact line boundary leaves no record for any shipped verifier to reject. The receipts are absent evidence, not invalid evidence. Catching that class needs a shipped helper that runs the meta cross-check (receipt_count and last_receipt_hash against the segment content) which the new tests exercise by hand.
