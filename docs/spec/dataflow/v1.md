Raucle Data-Flow Enforcement
============================

Version: v1 (Draft 1)

Conformance claim language: an implementation of this spec MUST satisfy the
semantics below and replay the corpus vector
`standards/test-vectors/dataflow_v1_01_taint_denies_destination.json` to the
recorded verdicts.

## 1. What this adds

The provenance layer already propagates taint tags monotonically across the
receipt DAG (`docs/spec/provenance/v1.md` §4): every child inherits the taint
set of its parents unless an explicit sanitisation clears an authorised tag.
Per-call enforcement, however, was not data-flow-aware: gate decisions
considered only the call itself (tool, agent, arguments, constraints).

This spec adds one policy rule kind, `deny_from_chain_taint`, with
deterministic per-call semantics:

> Deny any call whose destination class is D whenever any prior tool output in
> the SAME task/delegation chain carries taint tag T, subject to the
> destination-class allow-listing described below.

## 2. Policy DSL

The key is rule-level (a sibling of `constraints`), like all rule kinds:

```yaml
version: 1
issuer: acme.bank
policies:
  - tool: transfer_money
    agent_id: agent:pay
    constraints:
      allow:
        from_account: ["ACC-001"]
    deny_from_chain_taint:
      taint_tags: ["untrusted_user"]
      destination_classes: ["payment:external"]
      # optional allow-list: when present, EVERY destination class NOT listed
      # denies while chain taint applies (fail-closed allow-listing)
      allow_destination_classes: ["payment:internal"]
```

Validation (a policy file that violates any of these refuses to load):

- `taint_tags` is a non-empty list of non-empty strings;
- at least one of `destination_classes` (non-empty string list) or
  `allow_destination_classes` (non-empty string list) is present;
- `allow_destination_classes`, when present, is non-empty.

## 3. Chain state

The chain state at decision time is the ordered list of tool outputs the
gateway has been told about for the call's `trace_id` (the task/delegation
chain). Outputs are recorded explicitly - once a gated call's output is
known - via the gateway's `record_chain_output(trace_id, tool, taint_tags)`;
each entry carries the tool name and the taint tags that output carries. The
state changes only through this recording, so a decision replays the SAME
chain state deterministically (no side-channel input): the same (rule, prior
outputs, destination class) triple always yields the same verdict.

## 4. Per-call evaluation semantics

Given the replayed chain state and the call's `destination_class`:

1. A malformed (non-string or empty) taint tag ANYWHERE in the chain state
   denies the call outright with reason `data-flow rule: unknown taint tag in
   chain state (fail-closed deny)` — an unclassifiable taint cannot be proven
   NOT to reach the call.
2. No listed tag in the chain state allows the call, regardless of
   destination class: every call alone remains allowed.
3. With chain taint present:
   - an empty (unknown) `destination_class` denies with reason
     `data-flow rule: unknown destination class (fail-closed deny)`;
   - when `allow_destination_classes` is present, every destination class not
     on the allow-list denies;
   - otherwise a destination class in `destination_classes` denies.

A covering deny reasons with the matched taint tag, the destination class and
the basis, e.g.:

```
data-flow rule: taint tag 'untrusted_user' in chain state with destination class 'payment:external' in denied destination classes (fail-closed deny)
```

## 5. Enforcement point and composition

- The deny is evaluated at the gate for the matched rule, BEFORE constraint
  evaluation and approval/escalation paths: a data-flow deny cannot be
  bypassed by an escalation, and the rule kind can only ever DENY — it never
  widens the authority a capability token grants.
- The deny composes with the existing constraint machinery without changing
  its per-call semantics: rules without the kind behave exactly as before;
  rules with both a kind and constraints keep every constraint verdict, and
  the data-flow layer only adds denies.
- A rule with the kind but an UNUSABLE chain state (missing `trace_id`)
  denies fail-closed with reason `data-flow rule: no chain state available
  (trace_id missing) - fail-closed deny`.
- Denies are receipted like every other gate deny, with the named reason in
  the receipt (x_gate), citing the rule id.
- HTTP surface: the gate request accepts an optional `destination_class`
  field, evaluated identically.

## 6. Test vectors

`standards/test-vectors/dataflow_v1_01_taint_denies_destination.json` pins the
acceptance scenario: two-call chain, call 1 allowed and its output carries
`untrusted_user`, call 2 targets `payment:external` under a `T denies D` rule
— call 1 allows, call 2 denies, and call 2 alone (fresh chain state) allows.
