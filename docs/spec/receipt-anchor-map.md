# Receipt-anchor guarantee matrix and chain-to-anchor map

- **Status:** Proposed (issue 342 implementable slice; ADR 0009 required-validation items 1 to 6 of this lane)
- **Date:** 2026-11-26
- **Version:** 1
- **Scope:** the receipt ledger, its evidence artifacts, and the transparency proof paths above the segmented receipt store
- **Programme:** [Enterprise Readiness Programme #107](https://github.com/epic28-ltd/raucle-agent-assurance/issues/107), [Raucle issue #342](https://github.com/epic28-ltd/raucle/issues/342)
- **Boundary:** implements the ADR 0009 required-validation items that belonged to this lane: the artifact-to-anchor mapping, tamper-class regression coverage, independent verifier fixtures and the proof-cost benchmark. The crash-and-rollback slice of the segmented STORE itself is issue 344 / PR 365 (`tests/test_receipt_store_crash_recovery.py`); that slice is cited, never duplicated. The offline verifier's CLI surface and JSON output contract belong to the verifier lane and are not touched here.

Classification: `PROVEN` marks behaviour asserted by a named, passing test id (all ids on this branch run in the canonical suite). `GAP` marks an honest absence: no mechanism in the current code covers the class, and the named pin test documents the exact behaviour an assessor would observe. Nothing here is a certification. No claim of WORM or immutable storage is made anywhere in this document: receipt persistence is append-oriented and fsynced, and every "sealed"/"read-only" posture below is a local operational measure, not an immutability guarantee.

## 1. Chain-to-anchor map: what each mechanism actually anchors

Derived from the code, not the module docstrings: `raucle/receipt_store.py`, `raucle/audit.py` (HashChainSink, AuditVerifier, MerkleFrontier), `raucle/provenance.py` (ProvenanceVerifier), `raucle/transparency.py` (SCITTAnchorClient, compute_chain_head, verify_transparency_anchor, verify_log_inclusion, verify_log_consistency, compute_log_entry_hash), `raucle/receipt_index.py`.

| # | Artifact (shape) | Offline verification | Anchors | Does NOT anchor | Evidence |
|---|---|---|---|---|---|
| A1 | Signed provenance receipt: one JWS + `receipt_hash` per ledger line (a receipt chain is JSONL of `{"receipt_hash","jws"}`) | `ProvenanceVerifier.verify_chain` (signature, stored-hash recompute, DAG, taint, bounds) | Each receipt's signed content and its declared parents, individually | Completeness of the presented collection, presentation order, equivalently-legal forked collections | A2 below |
| A2 | Receipt-ledger segments + seal sidecars (`seg-NNNNNN.jsonl` + `.meta`; `receipt_count`, `last_receipt_hash`, Ed25519 signature over canonical meta) | `verify_seal_meta(meta, seal signer public key)` + the count/final-hash reconciliation of the presented segment against the meta | Segment membership at seal time: how many receipts and which final hash the sealed segment held | Anything after the seal; the meta's own truthfulness is held to the sealing key only | `verify_seal_meta` refusals: `tests/test_receipt_store.py::TestSealMetaSignature::test_verify_seal_meta_rejects_tampered_meta`; reconciliation: `TestSealReconciliation::test_presented_segment_shorter_than_its_seal_is_nameable` |
| A3 | Audit hash chain (HashChainSink JSONL: signed `chain_meta` header, hash-linked event records, Merkle-rooted signed checkpoints) | `AuditVerifier.verify_chain` (index continuity, prev-hash links, per-record stored-hash recompute, checkpoint Merkle roots, key-id pinning, `AUDIT-DOWNGRADE`, `AUDIT-TRUNC`) | Interior integrity and, with signed checkpoints under a pinned key, the trailing boundary of the event stream | The receipt ledger (a different artifact shape, A1/A2); anything the chain format does not express | `TestAuditChainTamperClasses` rows in section 2; pre-existing named refusals in `tests/test_sec_audit.py` |
| A4 | Receipt index (`receipt_index.py`, SQLite) | None required: it is a disposable projection | Nothing. It is never evidence and must never override the chain; repair is `rebuild_from_store` | Anything | `tests/test_receipt_index.py::TestReceiptIndex::test_rebuild_from_store`, `test_rebuild_idempotent_no_duplicates` |
| A5 | SCITT head statement (`transparency.py`: `{statement.{entry_profile,chain_id,chain_head{index,hash}}}`, signature path) | `verify_transparency_anchor(chain_path, statement)` recomputing the head via `compute_chain_head` | Non-equivocation of the HEAD (final event index + final record hash) of the chain format `compute_chain_head` consumes: the HashChainSink event-chain format only | Interior completeness (a middle deletion leaves the head intact - the honest limit is named in section 2); truth or completeness of the underlying events; any receipt-ledger segmented file (they are refused, GAP 1) | `TestAnchoredRollbackAndEquivocation::test_rolled_back_chain_is_digest_mismatch_against_the_anchored_head`, `test_divergent_chain_from_one_trust_root_is_digest_mismatch`, limit pin `test_the_head_anchor_does_not_detect_middle_event_deletion`, GAP pin `test_a_receipt_segment_is_not_a_conformable_anchor_artifact`; anchoring itself (registration flow): `tests/test_transparency.py` |
| A6 | Hosted transparency-log entry + signed Ed25519 epoch checkpoint (per org; `compute_log_entry_hash`, `verify_log_inclusion`, `verify_log_consistency`, pinned operator key) | The log verifier APIs against the pinned operator key | That a receipt DIGEST was registered with this operator in this org, at a provable (org, sequence), with the log's append-only growth between two signed heads (consistency) | That everything was registered (withholding is the documented residual, `x2-transparency-log-v1.md` Honest limits); receipt content quality; any fork the verifier holds no retained material for (GAP 3) | `tests/test_transparency_log_verify.py` (round trips, named refusals, cloud cross-repo fixture `test_cloud_fixture_inclusion_proof_verifies`); this lane: `test_rewritten_log_history_contradicts_the_retained_registration_proof`, `test_forked_log_contradicting_a_retained_proof_is_refused_by_name`, `test_consistency_growth_binding_refuses_a_rewritten_applied_segment`, fork limit pin `test_two_forks_without_retained_material_both_verify` |
| A7 | WORM receipt archive (`raucle/worm.py`) | Own tests in the WORM lane (out of this map's proof paths) | A retention-modelled archival copy of chain artifacts (append-oriented, hash-chained write log; the in-software model of Object-Lock compliance-mode semantics) | Hardware WORM or immutability: the archive models retention in software and is never an immutability claim | See the WORM lane's design ADR; classification only here |

Precise mapping sentence for auditors: the phrase "the receipt ledger is anchored" is false on at least one of the three readings. The audit hash chain head is anchorable (A5, today); individual registered receipt digests are anchorable via the hosted log (A6, today); the receipt-ledger segment head is NOT anchorable today (GAP 1) - the binding that exists for segments is the A2 seal reconciliation, which is local-key tamper evidence, not external non-equivocation.

## 2. Tamper-class matrix

Cell values: `PROVEN <test id>` where a mechanism covers the class; `GAP` where it does not, with the pin test id (the pin documents the CURRENT behaviour). The full six-class suite this table cites lives in `tests/test_receipt_tamper_evidence.py`.

| Layer (verifier) | Content tamper | Truncation (tail) | Deletion (interior) | Reorder | Rollback (shorter reconstructed chain) | Equivocation (forked chain, one trust root) |
|---|---|---|---|---|---|---|
| Receipt chain (`ProvenanceVerifier.verify_chain`) | PROVEN (per-receipt hash + signature): `tests/test_receipt_store_crash_recovery.py::...::test_tampered_record_in_sealed_segment_caught_on_verify` | GAP (pin: `TestReceiptLedgerTamperClasses::test_truncating_the_collection_verifies_the_remaining_records`; controls: A2 reconciliation, A5 head, A6 registrations) | PROVEN when the deleted receipt is cited: `TestReceiptLedgerTamperClasses::test_deleting_a_cited_parent_refuses_by_name` | GAP (pin: `...test_reordering_receipt_lines_is_not_tamper_evident_in_this_layer`; order evidence is A3/A6) | GAP (pin: `...test_truncating_the_collection_verifies_the_remaining_records`) | GAP (pin: `...test_two_divergent_collections_from_one_identity_both_verify`) |
| Withholding (receipt chain) | PROVEN for withheld parents of a presented child: `TestReceiptLedgerTamperClasses::test_withholding_the_parent_unresolves_the_presented_child`; withheld TAIL records are the truncation GAP above | | | | | |
| Segment seals (`verify_seal_meta` + reconciliation) | PROVEN meta tamper: `tests/test_receipt_store.py::TestSealMetaSignature::test_verify_seal_meta_rejects_tampered_meta`; forged meta: `TestSealReconciliation::test_forged_seal_meta_over_a_truncated_segment_refuses_by_name` | PROVEN reconciliation: `TestSealReconciliation::test_presented_segment_shorter_than_its_seal_is_nameable` | n/a (seal is per-segment; interior deletion shows in the count reconciliation like any shortening) | n/a (count + final hash unchanged by reordering) | PROVEN count/final-hash divergence | n/a (seal binds one segment; equivalently-legal forked segments are GAP 2) |
| Audit hash chain (`AuditVerifier.verify_chain`) | PROVEN: `tests/test_audit.py::TestAuditVerifier::test_tampered_record_detected` | PROVEN: `tests/test_sec_audit.py::TestAuditTruncation::test_truncating_signed_closed_chain_is_detected`, `test_truncating_tail_and_checkpoint_caught_by_required_head_checkpoint`; with a retained head: `test_expected_head_index_detects_truncation`, `test_expected_head_hash_detects_truncation` | PROVEN this lane: `TestAuditChainTamperClasses::test_deleting_a_middle_event_refuses_by_name`, `...::test_deleting_a_middle_event_breaks_the_checkpoint_binding` | PROVEN this lane: `...::test_swapping_two_event_records_refuses_by_name` | PROVEN this lane: `...::test_rolled_back_chain_passes_alone_and_refuses_against_the_retained_head` (passes alone; refused with the retained head, `AUDIT-TRUNC`) | PROVEN via the anchored-head comparison below (two signed histories from one root) |
| SCITT head statement (`verify_transparency_anchor`) | PROVEN refusal to anchor tampered material (head recompute): `tests/test_transparency.py::test_tampered_chain_refuses_to_anchor` | PROVEN: `TestAnchoredRollbackAndEquivocation::test_rolled_back_chain_is_digest_mismatch_against_the_anchored_head`; committed-fixture variant: `TestAuditChainAndAnchorFixtures::test_anchor_statement_refuses_a_rolled_back_chain` | GAP (pin: `...::test_the_head_anchor_does_not_detect_middle_event_deletion`; interior coverage is the A3 row above) | n/a (head is order-blind; reorder is the A3 row's class) | same as truncation (DIGEST-MISMATCH) | PROVEN: `...::test_divergent_chain_from_one_trust_root_is_digest_mismatch`; receipt-collection forks stay GAP row 1 |
| Hosted transparency log (`verify_log_inclusion` / `verify_log_consistency`, pinned operator key) | PROVEN entry binding: `tests/test_transparency_log_verify.py::test_doctored_entry_is_a_named_refusal`; this lane: `TestAnchoredRollbackAndEquivocation::test_consistency_growth_binding_refuses_a_rewritten_applied_segment` | PROVEN segment truncation vs head: `tests/test_transparency_log_verify.py::test_malformed_proofs_refuse_with_the_named_status` (truncated segment → `LOG-HEAD-MISMATCH`) | PROVEN retained-proof binding: `TestAnchoredRollbackAndEquivocation::test_rewritten_log_history_contradicts_the_retained_registration_proof`; fork refused with a retained proof: `...::test_forked_log_contradicting_a_retained_proof_is_refused_by_name` | PROVEN contiguity: `test_malformed_proofs_refuse_with_the_named_status` (non-contiguous → `LOG-CHAIN-BROKEN`) | same as deletion (a retained (sequence, digest) proof refuses the rewritten history) | PROVEN with a retained proof; GAP without retained material (pin: `...::test_two_forks_without_retained_material_both_verify`; GAP 3) |

Withholding (class standing alone): for the receipt chain it is resolvable-citation failure when a withheld record was cited (row 1) and silent otherwise (GAP, truncation controls). For the hosted log it is the documented residual ("the log proves what was registered, not that everything was", `x2-transparency-log-v1.md`); the retained registration proof (A6) is the positive-evidence control an auditor re-verifies after any suspected withholding, and there is no mechanism today that detects a record that was never registered (GAP 4).

## 3. Named gaps and follow-ups

1. **Receipt-ledger heads are not anchorable (A5 GAP).** `compute_chain_head` parses the HashChainSink event-chain format; a segmented receipt file (A1/A2 shape) raises a named refusal (`TestAnchoredRollbackAndEquivocation::test_a_receipt_segment_is_not_a_conformable_anchor_artifact`). Follow-up (raucle core, additive): a conformable head wrapper for the receipt ledger, or an anchored-seal profile (`receipt_count`, `last_receipt_hash`, sealing key) that a transparency service can register - versioned, with offline vectors per ADR 0009 decision 1. Until then, "SCITT anchors our chains" must be stated as "anchors audit-chain heads".
2. **Receipt-collection order and completeness are not tamper-evident in isolation (A1 GAPs).** The chain verifier binds content and parent DAG by design; completeness and order live with the seal reconciliation (A2), the audit chain (A3) and the log registrations (A6). Follow-up: deployment policy that pairs each exported receipt collection with its seal metas and the retained log proofs; no code change required by this map.
3. **Log equivocation needs retained material, and the verifier has no comparison parameter (A6 GAP).** Two forks signed by the same pinned operator key both verify alone when the verifier holds no retained proof or checkpoint (`test_two_forks_without_retained_material_both_verify`). ADR 0009's answer is independent checkpoint/proof retention plus an expected-checkpoint monitor; the natural API follow-up is an optional retained-checkpoint parameter on `verify_log_consistency` (or an equivalent deployment tool) that refuses a presented `from_checkpoint_jws` not equal to the retained bytes. NOT done in this slice: it widens the verifier's public contract mid-lane; named here as the follow-up for the next slice (and reported for the verifier-lane boundary in the PR).
4. **Withholding before the first anchor (A6/ADR residual).** A later checkpoint alone cannot prove records it never saw; shortening the anchor interval, independent witnesses and expected-volume monitoring are the ADR's deployment-policy follow-ups, unchanged by this map.
5. **SCITT statement signature path (A5, pre-existing).** Offline verification confirms digest match + signature-path presence; full COSE verification against a transparency root remains the transparency-v1 spec'd verifier wiring follow-up. Not this slice.
6. **`receipt_hash`-prefixed chains have no interior continuity (A1, design note).** Each receipt line is independently signed; the "chain" is a set with a parent DAG. This is why rows A1's completeness/order cells are GAPs while A3's are PROVEN - keep the two artifacts distinct in every operator narrative.

## 4. Proof-cost benchmark (indicative only)

`tests/test_receipt_anchor_bench.py` (marker ``bench``; deterministic workloads, bytes counted from the same verifier inputs, wall clock measured around single verification calls; the test asserts verification correctness only). One measurement on the lane dev host (Linux, 3.13 venv); re-run for current numbers; **no SLO claim, no performance claim - decision input only for ADR 0009's "measure before Merkle" gate.**

| measurement | proof bytes | verify ms |
|---|---|---|
| receipt chain, 16 receipts (full file) | 15,067 B | ~7.6 |
| receipt chain, 48 receipts (full file) | 45,691 B | ~15.7 |
| receipt chain, 96 receipts (full file) | 91,627 B | ~49.0 |
| transparency inclusion, log 64, target 1 (whole segment) | 23,724 B | ~1.5 |
| transparency inclusion, log 64, target 32 | 12,574 B | ~0.8 |
| transparency consistency, log 64, from 32 | 12,684 B | ~0.9 |
| transparency inclusion, log 256, target 1 (whole segment) | 93,005 B | ~4.7 |
| transparency inclusion, log 256, target 128 | 47,268 B | ~2.4 |
| transparency consistency, log 256, from 128 | 47,380 B | ~2.6 |
| audit hash chain, 64 events (full file) | 17,989 B | ~2.7 |
| SCITT anchored head, 64 events (statement check) | 267 B | ~1.5 |
| audit hash chain, 512 events (full file) | 133,470 B | ~14.7 |
| SCITT anchored head, 512 events (statement check) | 268 B | ~11.0 |

Reading, honestly labelled as one host's single run: at these scales the linear hosted-log proofs stay within a couple of multiples of the full-chain-file bytes while verifying 3x to 30x faster than a full receipt-chain verification of comparable material, and the anchored-head statement is hundreds of bytes for any of the measured chain sizes. The Merkle question stays open per ADR 0009: proof size at enterprise scale (10^5 to 10^7 entries) is not measured here; this benchmark is the seed, not the verdict.
